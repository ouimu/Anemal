# Grill — Per-Tenant Storage Provider: Google Drive Driver (Sub-project 2 of 3)

**Date:** 2026-07-23
**Gate:** CLAUDE.md Step 3.5 (mandatory, non-skippable)
**Inputs:** design (`2026-07-23-storage-google-drive-driver-design.md`, revised twice before grill — once after Step 2 pm-agent review, once after Step 3 BA REQUEST-CHANGES sign-off), BA sign-off (`2026-07-23-storage-google-drive-driver-ba-signoff.md`), live interactive interview with the user (non-technical Clinic Admin, present throughout), an independent adversarial pass by a second model (Fable) prompted against the live design + source code.

## Method

Grilled the design live with the user first (interactive Q&A on the callback-mounting mechanism's concrete implementability), then dispatched Fable independently to verify that finding from the code and hunt for anything else neither the pm-agent review nor BA sign-off had caught — explicitly instructed not to just re-confirm BA's existing G-1..G-6 list. Fable returned 10 new findings (N-1..N-10), all read against live source (`app.ts`, `settings.routes.ts`, `auth.middleware.ts`, `pet.service.ts`, `encryption.ts`, `env.ts`). Every finding was folded directly into the design doc rather than left as a follow-up — this record exists as the audit trail, not as an open list.

## Findings and resolutions

| # | Finding | Resolution |
|---|---|---|
| Live | BA's G-1 fix ("dedicated public sub-router at the same path") only closes the auth gap if registered *before* `app.use('/api/settings', settingsRoutes)` in `app.ts` — Express's `router.use(authMiddleware)` runs for every request entering that prefix regardless of whether a matching route exists, so a same-prefix router registered after it would still 401 Google's redirect. Confirmed real by Fable reading `app.ts`/`settings.routes.ts` directly (not assumed) — app.ts has been reordered before (see its own "before /admin" comment). | Callback moved to a **completely different top-level path sharing no prefix with any existing mount**: `GET /oauth/google/callback`, its own tiny router, order-independent by construction. User re-registers this as the Google Cloud Console redirect URI. Chosen provider-generic (`/oauth/<provider>/callback`) since sub-project 3 (OneDrive) needs the identical pattern next. |
| N-1 | **(High, functional bug)** Drive allows duplicate same-named files and `files.create` never replaces — but pet photos use a *stable, overwrite-in-place* key. As originally designed (`files.create` only), every photo replacement would create a duplicate instead of replacing it; `read()`/`exists()` via list-by-name would return an arbitrary one of several. | `save()` now: list-by-name-in-parent → `files.update` (same file ID) if found, else `files.create`. Stated explicitly that Drive has no temp-then-rename analog — `files.update` is this driver's atomicity story. |
| N-2 | **(High, isolation)** "Each tenant = a separate Google account, no cross-tenant Drive to escape into" is not enforceable — nothing prevents the same Google account being connected to two Anemal tenants. Under the original unprefixed `Anemal/emr`, `Anemal/photo` tree, two tenants sharing an account would see/overwrite each other's files; additionally Google's revoke operates on the account+client grant, so one tenant's Disconnect silently breaks another tenant sharing the same account. | Restored the tenant-scoped prefix inside Drive too — `Anemal/tenant-{id}/emr`, `.../photo` — closing the file-visibility half of the gap. The revoke-cross-breaks-the-other-tenant half is Google's grant model, not preventable app-side; documented as an accepted risk (degrades to the normal reconnect-needed status on the other tenant's next operation). |
| N-3 | **(High, race)** The nonce-based replay protection as worded ("deleted/marked-consumed the first time callback successfully verifies it") is a verify-then-mark sequence — two near-simultaneous callback requests with the same `state` could both pass the check before either marks consumed. | Required as a **single atomic statement**: `UPDATE ... SET consumedAt = now() WHERE nonceHash = ? AND consumedAt IS NULL`, affected-rows must equal 1, executed before the code exchange. New `OAuthConnectNonce` table (provider-generic, reused by sub-project 3) mirrors the existing `RefreshToken` rotation pattern rather than inventing a new one. |
| N-4 | **(Medium, race)** Silent access-token refresh writes back to `TenantStorageConfig`. If an in-flight operation's refresh completes *after* the admin disconnects (row nulled per G-4b), the write-back would resurrect an encrypted token on a now-`local` row. | Write-back is a **conditional update** (`WHERE provider = 'google_drive' AND googleRefreshTokenEncrypted IS NOT NULL`), silently dropped if it doesn't match — never retried, never errored. |
| N-5 | **(Medium, key hygiene)** Signing `state` with the raw `SETTINGS_ENCRYPTION_KEY` (the same live AES-256-GCM data-at-rest key) widens that key's blast radius to a signing bug and couples its rotation to OAuth-state validity. | `state` signed with `HKDF-SHA256(SETTINGS_ENCRYPTION_KEY, info: 'oauth-state-hmac-v1')` — no new secret provisioned, but cryptographically separate from the data-at-rest key. |
| N-6 | **(Medium)** Missing/misconfigured `GOOGLE_OAUTH_CLIENT_ID`/`SECRET` at runtime would silently produce a broken consent URL, landing a non-technical admin on Google's own confusing `invalid_client` error page. | `/authorize` checks both are configured before building the URL; returns a clean `503 GOOGLE_OAUTH_NOT_CONFIGURED` instead. Deliberately *not* added to boot-time required-env validation (would brick non-Drive-using deployments) — checked lazily at request time. |
| N-7 | **(Medium)** The design didn't say where to redirect when `state` itself fails signature/expiry verification — and per G-2a, the subdomain embedded in an *invalid* state cannot be trusted either. | That one failure branch redirects to a fixed, server-configured default origin (never a value read out of the untrusted `state`). |
| N-8 | **(Low-medium, race, accepted)** Two simultaneous first-uploads to the same not-yet-created per-record subfolder can both miss the existence check and both create it, splitting files across two identically-named folders. | Accepted, same not-fatal posture as the folder self-heal case — per-record subfolders are created at most once per record's lifetime, not a hot path. Not fixed with locking in this sub-project. |
| N-9 | **(Low-medium)** Within the 10-minute `state` window, the initiating admin could be deactivated or the tenant suspended — the callback never passes through `authMiddleware`'s normal active-user/active-tenant checks (it can't; it has no JWT). | Required AC: re-verify the user is active, still holds `clinic.integrations.edit`, and the tenant is active, immediately before persisting — not merely at `/authorize` time. |
| N-10 | **(Low, hygiene, accepted)** `prompt=consent` mints a fresh refresh token every connect; reconnecting without disconnecting first leaves the *previous* refresh token valid at Google indefinitely. | Callback best-effort-revokes the previous stored refresh token (if any) before overwriting with the new one on a successful reconnect — logged on failure, never blocking. |

**Checked and explicitly found non-issues (documented so they aren't re-litigated):** classic OAuth login-CSRF (an attacker binding a victim tenant to the attacker's own Drive) — bounded because `/authorize` is authenticated and `state`'s `tenantId` comes from the issuer's own session, so an attacker can only mint state for a tenant they already administer; CORS — irrelevant, the callback is a top-level browser navigation, never an XHR target; in-flight driver operations during a disconnect (as distinct from N-4's token write-back) — correctly degrade to the existing `StorageUnavailableError` contract, no new handling needed.

## Outcome

All findings (the live-interview mounting-order issue, plus Fable's N-1 through N-10) resolved and folded directly into the design doc — Architecture, Data model (new `OAuthConnectNonce` table, tenant-scoped folder IDs), API/permission, UI, and Error handling sections all updated. No open findings remain. This grill record + the design's revision history stand as the audit trail; recorded against ADR-0023 (Google Drive is sub-project 2 of the same per-tenant BYO storage architecture).
