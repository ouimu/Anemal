# Design: Per-Tenant Storage Provider — Google Drive Driver (Sub-project 2 of 3)

**Date:** 2026-07-23
**Status:** Draft — pending BA sign-off + grill (CLAUDE.md Step 3/3.5)
**Parent goal:** Each clinic picks where its EMR attachments + pet photos live. Sub-project 1 (custom network-share/SMB driver): driver core merged to `main` as PR #46; API + UI (`updateStorageConfig`, `GET/PUT /clinic/storage-config`, the Storage settings page + switch-confirmation dialog) is committed on the shared `feature/tenant-storage-provider` branch as PR #47, **not yet merged to `main`**. This sub-project continues on that same branch (locked single-branch decision) and builds directly on top of that already-committed surface — safe to do locally since the code exists on the branch, but `main`/the roadmap should not describe Sub-PR B as shipped until #47 actually merges, and this sub-project's own PR should not be openable/mergeable ahead of #47. This sub-project = Google Drive, using the clinic admin's own Google account, OAuth-based. Sub-project 3 (OneDrive) follows the same pattern.
**Builds on:** ADR-0022 (`StorageDriver` interface), ADR-0023 (`TenantStorageConfig` table, `getStorageDriver(tenantId)`, switch-confirmation UI pattern — all from sub-project 1).

## User decisions (locked — confirmed live with the user 2026-07-23, do not re-litigate)

1. Build order: custom-path → Google Drive → OneDrive, all on one branch (`feature/tenant-storage-provider`), same locked decision from sub-project 1.
2. OAuth scope: `drive.file` (app only sees files it creates — narrower than full `drive` scope, no reason surfaced to need broader access).
3. Google Cloud OAuth client already created by the user (project "Anemal Access GDrive") — Client ID/Secret stored in `src/backend/.env` as `GOOGLE_OAUTH_CLIENT_ID`/`GOOGLE_OAUTH_CLIENT_SECRET`. **Grill finding (required — supersedes decision 3's original registered URI):** the callback route moves to a top-level path outside `/api/settings` entirely — `GET /oauth/google/callback` — to remove a fragile router-mounting-order dependency found during the grill (see Architecture section). The user must re-register the redirect URI in Google Cloud Console as `http://localhost:4000/oauth/google/callback` (dev; production URI added as a second authorized URI at deploy time, out of scope here). Chosen as a top-level, provider-generic prefix (`/oauth/<provider>/callback`) specifically because sub-project 3 (OneDrive) will need the identical pattern — one path shape, no second Google-Console-style migration per provider.
4. Callback UX: **interstitial page** ("Connecting..." shown briefly) before redirecting back to `/settings/storage` — not an instant silent redirect. Rationale (user): visible feedback that something is happening.
5. Folder structure: one root **"Anemal"** folder auto-created in the admin's Drive on first connect. **Grill finding N-2 (required — revises the original "no prefix needed" reasoning):** the assumption "a Drive account is already a single tenant's own account" does not hold — nothing prevents the same Google account being connected to two different Anemal tenants (e.g. one person administers two clinics), and Google's `drive.file` visibility is scoped per OAuth-client-plus-account, not per individual grant — so two tenants sharing one Google account would see and could overwrite each other's files under an unprefixed tree, and one tenant's Disconnect (which revokes the account's grant at Google) would silently break the other tenant's connection too. Fix: **keep the tenant-scoped prefix** — `Anemal/tenant-{id}/emr/` and `Anemal/tenant-{id}/photo/` — restoring the same per-tenant namespacing the local/SMB drivers already rely on, even under a shared account. The cross-tenant *grant-revocation* hazard (disconnecting in one tenant can break another tenant sharing the same Google account) is Google's grant model, not something the app can prevent — documented as an accepted risk in Error Handling below, not silently ignored.
6. Connection status: checked **live, on every page-load** of Clinic Settings → Storage (a cheap Drive API call), shown as a green/red indicator. No background polling/scheduled health checks.
7. Disconnect/switch-away: reuses the **existing switch-confirmation dialog** from sub-project 1 (no new confirmation UI) — additionally revokes the Google token server-side as part of that same save. No auto-reconnect after a confirmed disconnect (Google's own security model requires the admin to re-consent through Google's screen; this cannot be bypassed or automated).
8. Error handling: same locked parent decision as sub-project 1 — Drive unreachable/quota/auth failure at upload/read time surfaces as an error, never silently falls back to local.

## Architecture

**New driver: `GoogleDriveDriver`** (implements the existing `StorageDriver` interface, alongside `LocalDiskDriver` and `SmbShareDriver`):
- Uses Google's official `googleapis` Node client (OAuth2 + Drive v3), wrapped behind a thin `google-drive-client.ts` seam — mirrors the `smb-client.ts` pattern from sub-project 1 so `GoogleDriveDriver`'s own tests run against a fake client, zero real network dependency.
- Constructed per-operation from the tenant's stored (decrypted) `{accessToken, refreshToken}` — the underlying `google-auth-library` OAuth2Client handles silent access-token refresh using the refresh token when the access token has expired; a refreshed access token is written back to `TenantStorageConfig` after use (single point of persistence, not a shared in-memory cache — consistent with "no caching of TenantStorageConfig" from sub-project 1, this is a token refresh not a config cache). **BA finding G-4a (required):** this write-back goes through the same `encryptField` helper and the same tenant-scoped repo as every other write to this table (`tenantId` never taken from anything but the resolved driver context) — and is **explicitly exempt from the `settings_audit_log`-on-write rule** (ADR-0023 R-4): it is a silent system token refresh, not an admin-initiated config change, and auditing every refresh would flood the log with non-events. **Grill finding N-4 (required):** the write-back is a **conditional update** — `WHERE tenantId = ? AND provider = 'google_drive' AND googleRefreshTokenEncrypted IS NOT NULL` — and is silently dropped (not retried, not errored) if that condition doesn't match. This prevents a race where an in-flight operation's token refresh completes *after* the admin has disconnected (row already nulled by G-4b), which would otherwise resurrect an encrypted token onto a row whose provider is no longer `google_drive`. (Note: the live status check on `GET /clinic/storage-config`, reachable by any `clinic.profile.view` holder per BA §3.5, can itself trigger this same refresh+write-back — intentional, not a separate concern.)
- **Grill finding N-1 (required — corrects the original `files.create`-only design):** Google Drive allows multiple files with the same name in one folder and `files.create` never replaces an existing file — unlike `LocalDiskDriver`'s temp-then-rename or `SmbShareDriver`'s equivalent, Drive has no filesystem-level "overwrite in place." This matters concretely for pet photos, which use a **stable, overwrite-in-place key** (`photo/pet-{id}.jpg` — the whole point of the local/SMB drivers' design). `save(key, body, contentType)` must therefore: (1) resolve/create the parent folder path (`Anemal/tenant-{id}/emr/42/` or `.../photo/`), (2) `files.list` for an existing file with that exact name in that parent, (3) if found, `files.update` (media upload) on that file's ID — replacing content in place, same Drive file ID, no duplicate; (4) if not found, `files.create`. This is Drive's actual atomicity story for this driver — there is no temp-then-rename analog, and the design must not imply one.
- Folder IDs for `Anemal`, `Anemal/tenant-{id}`, `Anemal/tenant-{id}/emr`, `Anemal/tenant-{id}/photo` are cached in `TenantStorageConfig` (looked up/created once, reused) — deeper per-record subfolders (e.g. `emr/42/`) are resolved per-operation (not worth caching, low call volume per record). **Grill finding N-8 (accepted, documented — not fixed):** two near-simultaneous first-uploads to the same not-yet-created per-record subfolder (e.g. two attachments uploaded to medical record 42 in the same instant) can each miss the `files.list` check and both `files.create` the `emr/42/` folder, producing two identically-named folders that split files between them. Accepted with the same not-fatal posture as the folder self-heal case (Error Handling) — low-likelihood (per-record subfolders are created at most once per record's lifetime, not a hot path), not fixed with locking in this sub-project; revisit only if it's observed in practice.
- `read(key)`: `files.get` with `alt=media`.
- `delete(key)`: `files.delete`. Idempotent — a 404 from Drive is treated as already-deleted, not an error (same contract as `LocalDiskDriver`/`SmbShareDriver`).
- `exists(key)`: `files.list` filtered by parent + name.
- Every method maps Drive's error shapes onto the existing `StorageNotFoundError`/`StorageUnavailableError` pair (same contract sub-project 1 established) so `pet.service.ts`/`emr-attachment.service.ts` need zero changes — they already only know about `StorageDriver`, not which concrete driver is active.
- `getStorageDriver(tenantId)` (existing function, sub-project 1) gets one more branch: `provider === 'google_drive'` → `new GoogleDriveDriver(...)`.

**OAuth connect flow (2 new routes — everything else reuses sub-project 1's `/clinic/storage-config` infrastructure):**
- **Corrected during Step 2 review (2026-07-23):** the frontend cannot do a plain browser navigation straight to a `requirePermission`-guarded backend route — Anemal's auth model is a Bearer JWT held in frontend state, which a bare GET navigation carries no header for. Fixed by splitting the hop: `GET /clinic/storage-config/google/authorize` (permission: `clinic.integrations.edit`, called as a normal authenticated `fetch`/XHR from the frontend, same as every other protected read) returns **JSON** `{ url: string }` — the Google consent URL — instead of issuing a redirect. The frontend then does the actual browser navigation itself (`window.location.href = url`) directly to Google, never to our own backend route. This keeps every protected call inside the normal Bearer-auth path; only the truly unauthenticated hop (Google → our callback) has no `Authorization` header, and that hop is already covered by the signed `state` param below.
  - Consent URL built with: client ID, `drive.file` scope, `access_type=offline` **and `prompt=consent`** (offline alone does not reliably re-issue a refresh token on a *second* consent after a prior disconnect/revoke — forcing the consent prompt guarantees a fresh refresh token every connect, not just the first ever).
  - `state` param: signed, embeds `tenantId`, `userId`, **the tenant's canonical frontend subdomain resolved server-side from `tenantId`** (see BA finding G-2a below — never taken from a client-supplied header/param), a single-use nonce (see G-2b), and an issued-at timestamp with a 10-minute expiry.
  - **Grill finding N-6 (required):** `/authorize` checks `GOOGLE_OAUTH_CLIENT_ID`/`GOOGLE_OAUTH_CLIENT_SECRET` are actually configured **before** building the consent URL — if either is missing/empty, returns `503 GOOGLE_OAUTH_NOT_CONFIGURED` rather than letting the admin land on Google's own confusing `invalid_client` error page mid-flow. The env vars are intentionally **not** added to `config/env.ts`'s required-at-boot validation (that would brick every deployment not using Drive) — checked lazily, at request time, in `/authorize` and again before the callback's code exchange.
  - **Grill finding N-5 (required):** `state` is signed with **HMAC-SHA256 over a purpose-derived key** — `HKDF-SHA256(SETTINGS_ENCRYPTION_KEY, info: 'oauth-state-hmac-v1')` — not the raw `SETTINGS_ENCRYPTION_KEY` directly. No new secret to provision (still derived from the one existing key), but keeps OAuth-state signing cryptographically separate from the AES-256-GCM data-at-rest key: a bug in one path can't touch the other, and the two can be rotated independently later if needed.
- **BA finding G-2a (required fix):** the redirect origin embedded in `state` must be derived **server-side inside `/authorize`** from the authenticated request's own `tenantId` → that tenant's known subdomain (the same lookup the app already does for tenant resolution elsewhere) — never from a request header, query param, or `Referer`, even though the value ends up signed. Signing does not sanitize an attacker-chosen value; it only proves *we* signed it. A client-controlled signed redirect target is a signature-blessed open redirect.
- **BA finding G-2b + grill finding N-3 (required — the exact consume mechanism):** `state` carries a single-use nonce. `/authorize` records it server-side by reusing the existing `RefreshToken`-style rotation pattern (a small table: nonce hash, `tenantId`, `userId`, `expiresAt`, `consumedAt` nullable) rather than inventing a new mechanism. **The consume step at `/callback` must be a single atomic statement** — `UPDATE ... SET consumedAt = now() WHERE nonceHash = ? AND consumedAt IS NULL`, checking the affected-row count equals 1 — executed **before** the code exchange, not a separate check-then-mark (a verify-then-mark sequence lets two near-simultaneous callbacks with the same `state` both pass the check before either marks it consumed). An affected-row count of 0 (already consumed, or never existed) is rejected identically to an invalid signature.
- **Grill finding — callback route relocated (supersedes BA finding G-1's original "dedicated public sub-router mounted at the same path" fix):** the grill found that even a dedicated public sub-router only closes the auth gap if it is registered in `app.ts` **before** `app.use('/api/settings', settingsRoutes)` — Express's `router.use(authMiddleware)` runs for every request that enters `settingsRoutes`'s mount prefix regardless of whether a matching route exists inside it, so a same-prefix public router placed *after* it would still 401. This ordering dependency is a silent-regression risk (app.ts routes have been reordered before). Fixed instead by moving the callback to a **completely different top-level path that shares no prefix with any existing mount**: `GET /oauth/google/callback`, registered as its own tiny router in `app.ts`, order-independent by construction. (User re-registers this as the authorized redirect URI in Google Cloud Console — see decision 3.) No rate limiting is added on this route in this sub-project — a rejected invalid-`state` request costs one cheap HMAC verification, low risk — but is called out explicitly here rather than left unexamined.
- `GET /oauth/google/callback` (public router, no JWT — the signed, single-use `state` param is the trust boundary, verified for **signature + ≤10-minute expiry + atomic nonce-consume + embedded tenant/user match, before anything is read or persisted**) — exchanges the returned `code` for `{accessToken, refreshToken}`, encrypts both (`SETTINGS_ENCRYPTION_KEY`, same helper as the SMB password), creates/reuses the `Anemal/tenant-{id}` root + `emr`/`photo` subfolders, persists `TenantStorageConfig` (`provider: 'google_drive'`, encrypted tokens, folder IDs), writes the same `settings_audit_log` entry pattern as every other config write, then redirects to `<server-derived-subdomain>/settings/storage/connecting`, which auto-redirects to `/settings/storage` after ~1.5s.
  - Consent-denied, code-exchange failure, and a replayed/already-consumed nonce are rejected with nothing persisted, redirecting to `<server-derived-subdomain>/settings/storage` with a distinct `?error=` code the frontend maps to specific copy (see Error Handling). **Grill finding N-7 (required):** on a **signature-invalid or expired** `state` specifically, the embedded subdomain cannot be trusted at all (that's the same reasoning as G-2a) — this one failure case redirects to a **fixed, server-configured default frontend origin** (or renders a plain 400 page), never to any value read out of the untrusted `state`.
  - **Grill finding N-9 (required AC):** before persisting anything, re-verify the initiating user is still active and still holds `clinic.integrations.edit`, and the tenant is still active — the 10-minute `state` window is short but non-zero, and the callback (unlike every authenticated route) never passes through `authMiddleware`'s normal active-user/active-tenant checks.
  - **Hygiene (BA finding G-5, non-blocking):** the authorization `code` in the callback URL query string is single-use and short-lived, but request-logging middleware must not log full callback URLs (query string included) — same posture already expected of any URL carrying a transient secret-bearing param.
- **Reconnect-over-existing-connection (grill finding N-10, non-blocking):** `prompt=consent` mints a fresh refresh token on every connect; if the admin reconnects without disconnecting first, the callback best-effort-revokes the *previous* stored refresh token (if any) before overwriting the row with the new one — logged on failure, never blocking the new connection — so a stale-but-still-valid grant isn't left alive at Google indefinitely.
- **Disconnect** (switching `google_drive` → anything else) does not get its own endpoint — it's handled inside the existing `updateStorageConfig` service function (sub-project 1): when the *current* row is `provider: 'google_drive'` and the new provider differs, call Google's token-revoke endpoint (`https://oauth2.googleapis.com/revoke`) with the decrypted refresh token, best-effort (logged on failure, never blocks the switch — the local config change is the source of truth, matching the existing "best-effort, logged" pattern for storage-layer failures elsewhere in ADR-0023). **BA finding G-4b (required):** in the same write, **null** `googleAccessTokenEncrypted`, `googleRefreshTokenEncrypted`, and the four folder-ID columns on the row — revoking at Google is not sufficient on its own; a stale encrypted refresh token must not be left at rest after a confirmed disconnect. **Grill finding N-2 (accepted risk, documented):** because Google's revoke call operates on the account+client grant (not a per-tenant concept Google is aware of), if the *same Google account* happens to be connected to more than one Anemal tenant, one tenant's disconnect silently breaks the other's connection too — the other tenant's next Drive operation will simply fail with the normal `StorageUnavailableError`/reconnect-needed status, which is a correct (if surprising) outcome given Google's grant model; not something the app can prevent, called out here rather than assumed away.
- **Status check**: `GET /clinic/storage-config` (existing endpoint) gets one more field, populated only when `provider === 'google_drive'`: a live `files.list` no-op call (cheapest possible authenticated call) — success → `connected: true`, `invalid_grant`/401 → `connected: false`, anything else (network blip) → `connected: true` with the check simply skipped/logged (a transient check failure must not falsely tell the admin to reconnect — same "don't read a blip as data loss" principle from sub-project 1's driver-level error handling, applied here at the status-check level).

## Data model

Extends the existing `TenantStorageConfig` table (sub-project 1) — no new table for this part, per that table's own design note ("kept out of `TenantSettings` specifically so future OAuth-token columns land here"):

| column | type | notes |
|---|---|---|
| `googleAccessTokenEncrypted` | text, nullable | AES-256-GCM via `SETTINGS_ENCRYPTION_KEY`; refreshed in place when the OAuth client silently renews it |
| `googleRefreshTokenEncrypted` | text, nullable | AES-256-GCM; long-lived, used to mint new access tokens |
| `googleRootFolderId` | text, nullable | Drive file ID of `Anemal/tenant-{id}` (grill finding N-2 — tenant-scoped, not the bare `Anemal` root) |
| `googleEmrFolderId` | text, nullable | Drive file ID of `Anemal/tenant-{id}/emr` |
| `googlePhotoFolderId` | text, nullable | Drive file ID of `Anemal/tenant-{id}/photo` |

`provider` column's value set extends from `local | custom_path` to `local | custom_path | google_drive` (already anticipated in sub-project 1's comment on that column).

**New table (grill finding N-3): `OAuthConnectNonce`** — deliberately provider-generic (not `google`-specific) since sub-project 3 (OneDrive) needs the identical single-use-nonce mechanism next:

| column | type | notes |
|---|---|---|
| `nonceHash` | text, PK | hash of the random nonce embedded in `state` (mirrors `RefreshToken.tokenHash` — never store the raw value) |
| `tenantId` | int | who initiated the connect |
| `userId` | int | which admin |
| `provider` | text | `'google'` (this sub-project); `'onedrive'` next |
| `expiresAt` | timestamp | `iat + 10 minutes` |
| `consumedAt` | timestamp, nullable | set atomically by the callback's single-use-consume statement (grill finding N-3) |

## API / permission

- `GET /clinic/storage-config/google/authorize`: `clinic.integrations.edit` (same as the existing `PUT /clinic/storage-config` — connecting a new provider is a write action). Called via a normal authenticated `fetch`, not a browser navigation — returns `{ url }` JSON, frontend performs the actual navigation to Google.
- `GET /oauth/google/callback`: no JWT/permission middleware — its own top-level public router (see Architecture — relocated from `/api/settings/...` during the grill to remove a router-mounting-order dependency). Trust boundary is the signed, single-use `state` param (server-derived tenant subdomain, atomically-consumed nonce, ≤10-min expiry — G-2a/G-2b/N-3), verified before anything is read or persisted.
- `GET /clinic/storage-config` (existing): response shape gains `connected?: boolean` (only present when `provider === 'google_drive'`).
- No new database read permission — reuses `clinic.profile.view` from sub-project 1.
- Access/refresh tokens: same rule as the SMB password — never returned by `GET`, `configured: boolean` stands in for them.

## UI

- Clinic Settings → Storage page: radio group gains a third option, **"Google Drive"**, alongside Local and Network share (sub-project 1's existing radio group, one more `<label>`).
- Selecting "Google Drive" (when not yet connected) shows a **"Connect with Google"** button instead of text fields — clicking it calls `GET /clinic/storage-config/google/authorize` (authenticated `fetch`, gets back `{ url }`), then the frontend sets `window.location.href = url` to leave the app for Google's consent screen (full-page navigation, not a popup — simpler, no popup-blocker edge cases).
- New standalone interstitial route/page (e.g. `/settings/storage/connecting`) — shows a centered "Connecting to Google Drive..." message with a spinner, auto-navigates to `/settings/storage` after a short fixed delay (~1.5s, just long enough to read).
- Once connected: same "connected" pill pattern as the SMB password field (sub-project 1) — shows the green/red status dot (from the live check) plus a **"Disconnect"** button. Clicking Disconnect reuses the exact same switch-confirmation dialog already built (provider effectively becomes `local` unless the admin picks another provider first) — no new confirmation UI to build.
- **BA finding G-3 (required) — data-custody note:** unlike SMB (bound to clinic-owned infrastructure), Google Drive binds the tenant's entire attachment/photo store to **one individual admin's personal Google account**. The connect flow's helper copy and the switch-confirmation dialog (when disconnecting or switching away) both state this plainly: "Files are stored in *this Google account's* Drive. If this account is lost or access is revoked, the clinic loses access to those files until reconnected." Parity with sub-project 1's folded-in data-custody note. Surfacing *which* account is connected (e.g. the email) is deferred — it would need a Drive scope broader than `drive.file`, a separate decision not assumed here.
- No raw hex colors, no emoji — reuses existing Compassionate Care tokens (green/red status dot uses existing `secondary`/`error` color tokens, not new ones).

## Error handling

- OAuth callback failures (user denies consent, `state` invalid/expired, code exchange fails) → redirect to `/settings/storage` with a query-param error the frontend reads and displays inline (e.g. "Google sign-in was cancelled or failed — try again"), nothing persisted.
- Runtime Drive failures (quota exceeded, network blip, revoked mid-session) during an actual upload/read/delete → surfaces as `StorageUnavailableError`/`StorageNotFoundError` exactly like sub-project 1's drivers, same retryable Thai message ("เข้าถึงที่เก็บไฟล์ไม่ได้ตอนนี้ ลองใหม่อีกครั้ง") — no separate Google-specific error copy needed at the storage-operation layer, only at the connect/status-check layer (which does need Google-specific copy, since "reconnect via Google" is a different remediation than "check the network share").
- Token-refresh failure (refresh token itself invalid/revoked) during a storage operation → same `StorageUnavailableError` path, since from the caller's perspective it's still "storage unreachable, retry" — the *specific* "you need to reconnect" messaging only shows up via the status-check on the Storage settings page, not buried in an EMR upload error toast.
- Revoke-on-disconnect failure (Google's revoke call itself fails) → logged, does not block the switch (see Architecture section — best-effort, matches existing pattern).
- **Orphaned folder-ID cache** (admin manually renames/deletes the `Anemal/tenant-{id}` folder or its children directly in their own Drive UI): a cached folder ID that Drive no longer recognizes is treated as "not found, not fatal" — same posture as file-level not-found — the driver re-creates the missing folder(s) on the next `save()` and updates the cached ID, rather than surfacing a hard error. Read/delete/exists against a now-missing folder still 404s normally (nothing to find). Renamed-but-not-deleted (grill finding N-8/G-6 family): the same self-heal creates a second folder rather than finding the renamed one — accepted, low-likelihood, not fixed in this sub-project.
- **Quota-exceeded** is deliberately *not* special-cased in this sub-project — it surfaces through the same generic `StorageUnavailableError` path as any other Drive failure, consistent with the precedent already accepted for SMB in sub-project 1 (a specific "your Drive is full" message would be a nice-to-have, not treated as a gap here).
- **Concurrent connect attempts** (e.g. an admin double-clicking "Connect with Google," or two admins racing): each produces its own signed `state`/nonce and its own callback; `TenantStorageConfig`'s `upsert` on `tenantId` (the PK) makes the last callback to complete the winner at the DB level — not treated as a risk given the actor pool is Clinic Admin only, and the outcome (one working connection, whichever completed last) is benign either way.
- **Shared-Google-account cross-tenant disconnect (grill finding N-2, accepted risk):** if the same Google account is connected to more than one Anemal tenant, disconnecting in one tenant revokes the shared grant at Google, and the other tenant's connection silently stops working — surfacing through its own next Drive operation as the normal `StorageUnavailableError` and a red status dot on its Storage settings page, i.e. it degrades the same way any other lost connection does, just with a surprising trigger. Not preventable app-side (Google's grant model is per account+client, not per Anemal-tenant); documented rather than assumed away.

## Performance (accepted, documented)

Same acceptance as sub-project 1: Drive API round-trips are slower than local disk; no caching layer beyond the folder-ID caching already described (which is structural, not a performance cache). Revisit only if measured to matter.

## Testing (high level — exact test list belongs in the write-plan)

- `GoogleDriveDriver` unit tests against a fake Drive client (mirrors `FakeSmbClient`): save/read/delete/exists happy path, folder auto-creation on first use, not-found vs. unavailable classification, **`save()` on an existing key uses `files.update` on the same file ID, not a duplicate `files.create`** (grill finding N-1 — the single most important new test in this sub-project, since a regression here silently breaks pet-photo replace).
- `getStorageDriver(tenantId)`: one more branch test, `provider = google_drive` → `GoogleDriveDriver`.
- OAuth callback integration tests: valid code exchange happy path (mocked token endpoint), invalid/expired `state` rejected (redirects to the fixed default origin, not a state-derived one — N-7), consent-denied redirect carries the right error param, folders created (tenant-scoped path) + config persisted + audit row written on success, **replayed/already-consumed nonce rejected** (N-3), **inactive user/tenant at callback time rejected** (N-9), missing OAuth env vars → clean 503 not a crash (N-6).
- Nonce-consume race test (N-3): two concurrent callback requests with the same `state` — exactly one succeeds, the other rejected as replay (not both succeeding, not both failing).
- Status-check tests: `connected: true` on a valid token, `connected: false` on a revoked/invalid one, transient failure does not flip to `false`.
- Disconnect/switch-away test: revoke call attempted, config still switches even if revoke fails (logged), **token + folder-ID columns are nulled in the same write** (G-4b).
- Token write-back race test (N-4): a token refresh that completes after a disconnect does not resurrect an encrypted token on the now-`local` row (conditional update, zero rows affected, silently dropped).
- No changes to existing local-disk/SMB driver tests or their call sites.
