System Overview

Anemal SaaS is a multi-tenant Software-as-a-Service platform for veterinary clinics. It supports both Web browser (reception counter) and Tablet (touch-first, consultation room) clients, with full multi-branch capability under a single subscription.

Multi-Tenancy Design

⚠ Iron Rule: Every SELECT, INSERT, UPDATE, and DELETE against tenant-scoped tables MUST include WHERE tenant_id = :currentTenantId. Enforced at three levels: database RLS policies, Express middleware (sets app.current_tenant_id), and explicit tenantId parameter in all repository functions.

Anemal uses a Shared Database, Shared Schema model. Each tenant is identified by a unique subdomain (abc-clinic.anemal.app) resolved at the API gateway.

4. Application Management (SaaS Platform Level)

This section covers the SaaS platform level — distinct from in-tenant admin functions. Operated by the Super Admin (system operator) via a separate control plane not subject to tenant RLS.

Tenant Onboarding

  1. Clinic registers at anemal.app/signup with clinic name, email, desired subdomain
  2. System validates subdomain uniqueness (3–50 alphanumeric chars)
  3. Atomic transaction: create tenants + first users record (role: admin)
  4. Trial period set: trial_ends_at = NOW() + 30 days
  5. Welcome email dispatched via SendGrid
  6. Clinic admin logs in at <subdomain>.anemal.app

Subscription Plans

PlanUsersBranchesKey Features
StarterUp to 31Auth, Pets, Appointments, EMR, Billing
ProfessionalUp to 103All Starter + Inventory, Reports, Grooming
Clinic PlusUnlimitedUnlimitedAll features + Blood Bank, Loyalty, API access

Plan limits enforced at API layer: exceeding user limit returns HTTP 402 Payment Required.

Super Admin Control Plane

  • View all tenants — plan, trial status, last activity (GET /platform/customers)
  • Suspend / reactivate a tenant (POST /platform/customers/:id/suspend|reactivate)
  • Override subscription plan or individual quotas (PUT /platform/customers/:id/quota)
  • Create / manage subscription plans with default quotas (/platform/plans)
  • Platform-wide metrics (active tenants, API call volume, error rates)
  • Access application logs for support escalation
Security: Platform operators use a separate auth flow (POST /platform/auth/login → platform-plane JWT). All operator actions are recorded in the immutable platform_audit_logs table. See Platform Console API for full endpoint reference.

FR-01: Authentication & Authorization

FR-01 Authentication & Authorization Phase 1 — Complete

Description

Secure login for clinic staff, JWT-based session management with tenant/branch context, role-based access control (RBAC), and optional login time-window restrictions per employee.

Process Flow

  1. User navigates to <subdomain>.anemal.app
  2. System extracts tenant from subdomain, validates tenant is active
  3. User submits email + password
  4. Server validates credentials (bcrypt compare)
  5. JWT Access Token (8h) + Refresh Token (30d) issued with payload: { userId, tenantId, branchId, role, exp }
  6. Client stores access token in memory; refresh token in HttpOnly cookie
  7. Every API request: middleware validates token, sets app.current_tenant_id PostgreSQL session variable
  8. If login time-window restrictions active and outside allowed hours → 403
  9. Token refresh: client sends refresh token → new access token issued
  10. Logout: refresh token blacklisted in Redis

Prerequisites

  • Tenant must be active (is_active = true)
  • User account must be active
  • User must belong to the subdomain's tenant

Additional Details

Rate Limiting: Redis counter per email address. After 5 failures in 15 minutes → 429 Too Many Requests. Counter resets on successful login.

Brute-Force Message Safety: Login failure always returns "Invalid credentials" — never reveals whether the email exists in the system.

Token Storage: Access token stored in browser memory (not localStorage). Refresh token in HttpOnly; SameSite=Strict cookie — immune to XSS theft.

Inactive Admin Guard: If the last active admin in a tenant tries to deactivate their own account, the API returns 409 Conflict to prevent tenant lockout.

Phase 8 — Two-Plane Authorization (RBAC restructure, in progress): Evolving to a two-plane model. Clinic plane (/clinic/*, /clinic-admin/*): users carry { userId, tenantId, branchId, roleId }; permissions resolved from role_permissions join table. Platform plane (/platform/*): platform_users (no tenant_id) for SaaS operations. Seven new DB models (2026-06-14): permissions, clinic_roles, role_permissions, user_roles, platform_users, plans, tenant_quotas. 49 permission codes seeded; system roles clinic_admin / doctor / clinic_staff seeded. T-5A-03/04/05 complete: permission.service.ts (resolvePermissions + in-memory cache), permission.middleware.ts (requirePlane + requirePermission factories), JWT extended with plane + permSetVersion. 5-B (route enforcement), 5-C (platform login/JWT) complete. T-5D-02/03/04 complete (2026-06-15): platform customer management API, plan CRUD + quota override endpoints, quota enforcement via assertCanAddUser/Branch/Owner(tenantId) — returns 409 QUOTA_EXCEEDED; suspended tenants return 401 TENANT_SUSPENDED at clinic login; platform_audit_logs migration added. See Platform Console API section below. Full spec: .claude/specs/RBAC_Platform_Restructure_Spec.md.

Testing Criteria

  • Valid login returns access + refresh tokens
  • JWT payload contains tenantId, userId, role
  • Wrong password → 401 (no hint about email validity)
  • Brute force: 6th attempt within 15 min → 429 Too Many Requests
  • Expired token → 401 with TOKEN_EXPIRED error code
  • Staff calling admin endpoint → 403 Forbidden
  • Tenant A token used against Tenant B → 403 Forbidden
  • Login outside time-window restriction → 403 Forbidden
  • Refresh token after logout → 401 (blacklisted in Redis)

FR-04 Appointment & Scheduler Phase 2 — Complete

Description

Calendar-based appointment management with daily/weekly views, doctor & room filtering, double-booking prevention, walk-in queue, and automated LINE/SMS reminders 24h before appointments.

Booking Flow

  3. Appointment created with is_walk_in = true, status in_progress

Status Transition

scheduled → confirmed → in_progress → completed
scheduled / confirmed → cancelled | no_show

FR-06: Inventory Management

FR-06 Inventory Management Phase 3 — Complete

Description

Real-time drug and product stock management per branch. Records every movement (in/out/adjustment/transfer) via a full stock ledger. Integrates with EMR prescriptions for auto-deduction and with Dashboard for low-stock / expiry alerts.

Stock-In (Receiving Goods) Flow

  1. Staff opens Inventory → Receive Stock
  2. Scans barcode (ZXing.js camera) or searches by name
  3. Enters: quantity, lot number, expiry date, cost price
  4. Creates stock_movements record (movement_type = 'in')
  5. branch_inventory.stock_qty updated for current branch

Auto Stock Deduction Flow

  1. Doctor adds prescription in EMR
  2. API checks branch_inventory.stock_qty ≥ prescribed qty in database transaction
  3. If sufficient: deduct stock + create stock_movements OUT record
  4. If insufficient: return 422 — prescription not saved
  5. Prescription cancelled → stock restored in reverse transaction

Alert Logic

  • Low stock: stock_qty < min_stock_qty → red badge
  • Expiry: expiry_date ≤ NOW() + 30 days → amber badge
